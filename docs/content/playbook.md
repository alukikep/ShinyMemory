# 内容生产手册

> 这份文档的目标：**让别人（或未来的我）不需要逐条讨论，就能按同样的标准批量生产一个角色的全部内容。**
>
> 规范细节在 [README.md](README.md)，数值在 [content-standards.md](../current/content-standards.md)，
> 系统在 [systems/](../systems/)。本文件只回答三件事：**怎么交给审查台、覆盖到什么程度、每类内容怎么写。**

---

## 0. 一句话流程

```text
角色卡 → 结构（TS）→ 草稿批次（审查台）→ 批量通过 → 构建 → 验收 → 记一笔
```

内容是**按块交付**的，不是按条讨论的。一个块的产出物是一个"批次包"，人只需要**通过 / 打回**。

---

## 1. 交付协议

### 1.1 我（生产者）每次交付什么

一个批次 = 一个块（3–8 条），交付时给这五项，**不多说**：

| # | 内容 | 例子 |
|---|---|---|
| 1 | 块编号与坐标 | `B3 · 真乃 · 偶像页 · 行动` |
| 2 | 草稿 id 列表 | `draft.activity.mano.extra_practice` … |
| 3 | 预检输出 | `npx tsx tools/content:validate` 与 `content:audit` 的结果 |
| 4 | 一句为什么 | 「专属行动不给粉丝，是为了不抢工作的生态位」 |
| 5 | 最多一个开放问题 | 「三个选项都同价，还是要一好一坏？」 |

### 1.2 人（审查者）只需要做什么

```text
通过 / 打回（打回时写一句原因）
```

打回不需要解释背景——一句「语气太活泼」就够，我按这句话重写，不辩解、不追问。

### 1.3 什么情况必须问，什么情况自己定

| 必须问 | 自己定 |
|---|---|
| 新增机制（新的条件/效果/系统） | 文案、选项措辞、结果文本 |
| 改已通过内容的语义 | 同一档位内的数值微调（±20% 以内） |
| 删除任何已通过内容 | 块内条数、排序、命名 |
| 数值档位本身的调整 | 解锁条件用哪个 flag |
| 跨角色的结构（日程、地点） | 冷却天数在档位内的取值 |

**没人可问时的默认动作**：选更保守的那个（数值更小、暴露更少、更容易改回来），并在交付说明里标一句「这里是按 X 定的」。

## 1.5 铁律：不许编造人设

**动手写任何角色内容之前，必须先读语料库。** 没有例外。

```text
ShinyGroup/SCTranslationData  →  data/story/<日文名>/
  W.I.N.G.編/   相遇、四季审查、决赛（相遇必读）
  G.R.A.D.編/   组合期
  S.T.E.P.編/   出道之前
  Landing Point編/
```

这一条是拿血换的：灯织第一版是靠印象写的，**相遇被我写成公园长椅，而原作是练习室**；
真乃的卡里也错写过「公园唱歌是本作改编」——那正是 W.I.N.G. 開場。

具体照做的顺序：

1. 读**相遇**那一章 → 招募链只能从这里改编，不能自创场景。
2. 读**出道前**（S.T.E.P.）→ 她的动机从这里来。
3. 读**和你接下来要写的场景最接近**的一章 → 抄句长和反应顺序，不抄台词。
4. 填角色卡（用 [character-card-template.md](character-card-template.md)，第 2 节必须写清相遇事实）。
5. 卡里每条判断都要能指回一个文件；指不回去的，标「待核」，别写进内容。

### 1.6 这条规则现在有机器门禁

```bash
npm run content:guard      # 已接进 content:validate，构建时会跑
```

它对**每个偶像**检查三件事：

| 检查 | 不通过会怎样 |
|---|---|
| 有角色卡 `docs/content/<id>/character.md` | 构建失败 |
| 卡里有「语料索引」，且**至少一个引用路径真实存在** | 构建失败 |
| 卡里有「回查记录」 | 构建失败 |
| 卡里有 **≥3 条原文引文**，且每条都能在所指文件里逐字找到（至少一条出自 W.I.N.G.編） | 构建失败 |

读没读是主观的，但**写不出三条逐字命中的原文**是客观的——抄三句真话就得打开文件。
这是"读过语料"能落到机器上的最低保证：造假成本高于读一遍。
写卡时语料索引要**一行一个完整路径**（`data/story/<角色>/...csv`），否则解析不到。

> 工程侧的约定（测试/截图分工、机器门禁、踩过的坑）在 [dev-guide.md](../current/dev-guide.md)。

## 2. 新角色接入：一份清单

按顺序做，每一步完成再进下一步。以「真乃」为样板。

| # | 步骤 | 产出 | 在哪 |
|---|---|---|---|
| 1 | **查语料** | 先把 W.I.N.G. / G.R.A.D. / S.T.E.P. / Landing Point 的该角色剧情读一遍，**相遇和关键转折都从原作改** | `SCTranslationData/data/story/<角色>/` |
| 1.5 | 角色卡 | 语气、称呼、阶段态度、OOC 对照、语料索引（台词要能指回文件） | `docs/content/<id>/character.md` |
| 2 | 偶像定义 | id、名字、组合、颜色、头像、成长曲线 | `src/core/content/idols/<id>.ts` |
| 3 | 角色日程 | 一周作息（她在哪、什么时候、能不能被工作顶掉） | `src/core/content/actors/<id>.ts` |
| 4 | 招募链 | 2 步剧情链 + 对话。**先定起步方式**（见下） | `storyChains.ts` + `dialogues/<id>.ts` |
| 5 | 训练与自由时间 | 至少 4 条偶像页行动 | 审查台批次 |
| 6 | 专属行动 | 1–3 条，挂在她作息的空档 | 审查台批次 |
| 7 | 日常话题 | 6–8 条闲聊，24 小时冷却 | 审查台批次 |
| 8 | 训练后事件 | 每个训练行动 1 条 | 审查台批次 |
| 9 | 工作线 | 她的属性对应的 2–3 份工作 | 审查台批次 |
| 10 | 长线剧情 | 3 步 + 分支，带一次解锁 | 审查台批次 + 结构 |
| 11 | 验收 | 跑 `npm run content:coverage` 补缺口，再在游戏里走一遍 | `npm run acceptance` |
| 12 | 记录 | 块表 + 一条经验 | `docs/content/README.md` |

**两种起步方式**（`src/core/content/starting.ts` 的 `idolStatus`）：

| 类型 | 开局状态 | 招募链做什么 | 例子 |
|---|---|---|---|
| **偶遇型** | `unknown` | 第一步"认识她"（设 known），第二步招募 | 真乃（公园听见她唱歌） |
| **档案型** | `known` | 第一步就是第一次见面，第二步让她答应 | 灯织、巡（制作人看档案选的人） |

档案型的链要写 `revealWhen: [{ kind: 'idolStatus', idolId, status: 'known' }]`，
这样**手册第一天就会出现"接下来要做什么"**。偶遇型不写 revealWhen，见过面才进手册。

第 2–4 步是结构（直接写 TS，不需要审查）；第 5–10 步全部走审查台。

## 3. 覆盖矩阵：做到什么程度算"全覆盖"

一个角色成熟时应该有这么多内容。**不是每个角色都必须满编**，但缺哪块要说得出来。

| 单元 | 建议条数 | 挂载点 | 必须性 |
|---|---:|---|---|
| 训练行动 | 3 | 偶像页 · 常驻 | ✅ 必须 |
| 自由时间 | 1 | 偶像页 · 常驻 | ✅ 必须 |
| 专属行动 | 1–3 | 偶像页 · 作息空档 | ✅ 至少 1 |
| 日常话题 | 6–8 | 偶像页 · 每天 3 次 | ✅ 至少 6 |
| 训练后事件 | 3–5 | 行动后 · `after` | ✅ 必须 |
| 地点事件 | 2–4 | 地点页 · `castPresent` | 🟡 建议 |
| 到达事件 | 0–2 | `entry.kind = arrival` | 🟡 可选 |
| 定时事件 | 0–2 | `trigger` | 🟡 可选 |
| 工作 | 2–3 | 事务所 · 有冷却 | ✅ 至少 2 |
| 剧情链 | 2 条（招募 + 长线） | 地点页 · 步骤 | ✅ 必须 |
| 对话 | 跟随剧情 / 事件 | — | ✅ 必须 |
| 物品 / 商店 | 跟随地点经济 | 店铺 | 🟡 按地点 |

**总时长目标**：一个角色从招募到"第一周有内容可做"，大约需要 **20–25 条**（不含对话节点）。

## 4. 写作配方

每类内容一份模板。所有数值都在 [content-standards.md](../current/content-standards.md) 里，这里只列**必填字段**和**最容易错的点**。

### 4.1 训练行动（偶像页）

```jsonc
{
  "id": "activity.<idol>.vocal",
  "name": "声乐课",
  "kind": "training",
  "target": "present-idol",
  "idolIds": ["<idol>"],          // 专属就写，全员通用可省
  "locations": ["practice_room"],
  "durationMinutes": 30,
  "timeWindows": [{ "fromMinute": 480, "toMinute": 1200 }],
  "cost": { "stamina": 12, "money": 120 },
  "effects": [
    { "kind": "attributeExp", "ref": "vocal", "tier": 3 },
    { "kind": "sharedStat", "stat": "stress", "delta": 5 }
  ],
  "resultTexts": ["…", "…"]        // 至少 2 条，别写一句循环用
}
```

- 档位：30 分钟 / 体力 10–15 / ¥120 / EXP +3 / 压力 +4–6
- ❌ 最常见错误：写 `fans`。训练不涨粉。

### 4.2 专属行动（偶像页 · 作息空档）

- 档位：30 分钟 / 体力 3–8 / **不花钱** / 信任 +5 / 属性 +1 / **不给粉丝**
- 她的作息里必须真的在那个地点那个时间，否则按钮永远不会出现
- 写法是「她在做自己的事」，制作人旁观或陪一段

### 4.3 日常话题（偶像页 · 闲聊池）

```jsonc
{
  "id": "<idol>.chat.<topic>",
  "actorId": "<idol>",
  "label": "今天怎么样",
  "text": "「……嗯。还行。」",
  "cooldownMinutes": 1440,
  "effects": [{ "kind": "attributeExp", "ref": "trust", "tier": 1 }]
}
```

- 每条 24 小时冷却、信任 +1
- 页面上只显示一个「聊两句」，**不要**给每条单独做按钮
- 一次 15 分钟、每天最多 3 次由系统管，内容侧不用重复限制

### 4.4 工作（事务所 · 面板）

```jsonc
{
  "id": "job.<name>",
  "name": "摄影棚拍摄",
  "locationId": "studio",
  "fromMinute": 600, "toMinute": 720,
  "pay": 1200,
  "check": { "ref": "expression", "difficulty": "E" },
  "failurePayRatio": 0.4,
  "cooldownDays": 2,
  "requires": [{ "kind": "fansAtLeast", "value": 500 }],   // 或 flag
  "hiddenUntilUnlocked": true,                              // 剧情解锁才用
  "effects": [
    { "kind": "fans", "value": 120 },
    { "kind": "attributeExp", "ref": "expression", "tier": 10 }
  ],
  "failureEffects": [{ "kind": "sharedStat", "stat": "stress", "delta": 12 }],
  "resultTexts": ["…"], "failureTexts": ["…"]
}
```

- **必须有检定**；没有检定的高报酬工作 = 签到
- **必须给粉丝和属性**；只给钱永远打不过 30 分钟零工
- 冷却 2 天（常规）/ 4 天（大活）
- 每个属性至少对应一份工作，否则那条属性没有出口

### 4.5 事件

```jsonc
{
  "id": "evt.<idol>.<anchor>",
  "title": "…",
  "after": { "ids": ["vocal"] },        // 偶像页行动用 after + afterIdol
  "afterIdol": { "ids": ["<idol>"] },   // 地点页行动改用 castPresent
  "chance": 0.4, "priority": 5, "once": true,
  "text": "…",
  "choices": [
    { "label": "…", "hint": "信任 +3", "effects": [...], "result": "…" }
  ]
}
```

- **事件没有文本变体**（对话才有）→ 高频锚点写多条 `once`，不要写一条循环
- 至少一个选项「有代价」
- 结果文本要回应选项，不是重复选项

### 4.6 对话与剧情链

- 对话节点可以有 `textVariants`（按条件换台词）
- 剧情链每一步：`locationId` + `timeWindow` + `dialogueId` + `actionLabel`
- 解锁用 `effects: [{ kind: 'flag', key: 'unlocked.xxx', value: true }]`
- **var / flag 键名要带命名空间**（`mano.slump`，不是 `mano_slump`）——体检规则 `var-namespace` 会拦
- 分支写进 var，第三步用 `textVariants` + `varAtLeast` 读它
- 长线剧情要有分支，选项之间**代价不同**而不是都 +1

### 4.7 物品与商店

- 物品：价格 200–800、`maxPurchases` 控制稀有度
- 商店：`itemIds` 决定货架（物品不反向引用商店）

### 4.8 卡面改编（P 卡 → 章节）

卡面剧情是碎片：原作里靠抽卡解锁、放在收藏库里，彼此没有时序。
本作把它们**重新组织成有触发点的章节线**——这是设计选择，不是还原。

**只做 P 卡**：P 卡自带 `choices`（三选一后合流），正好对上我们的对话结构；
S 卡是纯场景、没有选项，现阶段排除。

**改编分四级**：

| 级别 | 做什么 | 用不用 |
|---|---|---|
| L1 压缩 | 删语气词、重复、冗余旁白；句序与细节不动 | ✅ 主力 |
| L2 补桥段 | 加「为什么会有这一幕」「之后怎么样」 | ✅ 每章必须 |
| L3 重构 | 改因果、改关系 | ⛔ 不做 |

判定方法：**删掉这句话，读者会不会不知道发生了什么？** 会 → 不能删。

**选择点：跟着原作走**。卡面章的选择点数量和位置**必须和原作一致**——
原作每章 0 或 1 个三选一，我们就只保留那个，桥段里不加选择。

| 素材 | 原作选择点 | 我们就写 |
|---|---|---|
| カラフルサマー | 1（挑泳装） | 1 |
| 太陽のしずく | 0 | 0 |
| それはまだ純白な | 1（恋爱是什么） | 1 |
| 淹れたてコーヒー | 1（不是你的错） | 1 |
| なんでもない日の星空 | 0 | 0 |

**奖励要集中、要小**：不要每个节点都给加成。
一章的总量控制在 **信任 +3～4、单项属性 +1、压力 −5** 左右；
选择点的差别 ≤1 点（那是"口味"不是"正解"）；中间步骤不给效果，只在章末结算一次。

**四条硬约束**：

1. **情节与细节不改**——谁做了什么、结果如何一律不动，笑点和转折一句不能省。
2. **每章保留 ≥3 句原文台词，逐字不改**——这是「锚」，让读者认得出，也让机器能校验。
3. **压缩只删语气和重复，不删信息**。
4. **桥段只能补前后，不能改卡内因果**。

**锚点登记**：每做一章，在 `src/core/content/chapterSources.ts` 加一条：

```ts
{
  chapterId: 'meguru-swimsuit-1',   // 和剧情链 id 一致
  source: 'data/story/八宮めぐる/【夏に恋するピチカート！】八宮めぐる/カラフルサマー.csv',
  anchors: ['能全部都穿到就好了', '能上杂志的只有一件吧', '那就出门吧课程我晚点'],
}
```

`npm run content:anchors`（已接进 `content:validate`）查两头：

| 查什么 | 防什么 |
|---|---|
| 锚点在源文件里逐字存在 | 凭印象编台词 |
| 锚点活到了游戏对话里 | 压缩时顺手删掉 |

**一章 = 一段对话**（卡面章）。

```text
剧情链：1 步（一次触发，坐到底）
对话：  桥段开头 → 卡面正文 →（原作的三选一）→ 选项之后的整段 → 落点
```

**为什么不分步**：选项的影响要贯穿**整章剩余部分**。把一章拆成几步，
选择就只能管到那一步，后面的步骤照旧——这在视觉小说里是不成立的。
所以卡面章一律合成一条对话；跨天的章（闹掰之类）才需要多步 + 节奏。

一句话：**故事和细节照原样，句子可以压缩，首尾要我们自己接。**

### 4.9 卡面文件夹的读法（血泪）

一个 `【卡片名】/` 里**通常有 2–5 段**，每段是一个独立 commu（游戏相册里的一条）。
有的段是前后篇，有的毫无关系——**全部都要先看一遍再动手**。

**顺序在 commu id 里，不在文件名里**：

```text
2003005 01 0010   ← 第 0–5 位是卡号，第 7–8 位是段序号
2003005 02 0010
2003005 11 0010   ← 序号跳跃 = 可能换了类别
```

用工具列出来（不要靠 `ls`）：

```bash
npm run content:card -- "data/story/八宮めぐる/【夏に恋するピチカート！】八宮めぐる"
```

输出按序号排好，带每段行数和开头两句，直接能判断"哪几段是同一个故事"。

**事故记录**：做「泳装的颜色」时只 `ls` 到两个文件就当成了全部，
实际有 5 段；还把第 4 段（咖啡）当成了第 2 段（拍摄当天）。
结果把前篇当成了全篇，真正的落点（拍摄当天）漏掉了。

**单位口径**（不要再说错）：

| 单位 | 含义 | 数量（三人合计） |
|---|---|---|
| 张卡 | 一个文件夹 = 一张卡 | 113 张 |
| **段 / 场** | **一个 csv = 一章** | **368 段** |
| 步 | 一章里的剧情步骤 | 2–4 步 |

**卡内节号**：`chapterSources` 每条要写 `card: { title, index, total }`。
`content:anchors` 会用 commu id 的第 7–8 位**重新算一遍**再比对——填错会报红。
审查台靠它显示「夏に恋するピチカート！ · 第 1/5 节」，并按节号排序。

**交付顺序**：对话先送审 → 通过 → 再把章节链加进 `STORY_CHAINS`。
反过来（先接链）会让 `BASE_PACK` 引用不存在的对话，每个草稿预检都报 `dialogue-ref`。

**审阅边界**：对话草稿进审查台（台词、选项、结果）；
章节结构（步数、地点、时间窗、节奏）**不进审查台**，由 `content:anchors` 的结构校验兜底——
它查链是否存在、每步的对话与地点是否真的接上、以及"像卡面章却没登记锚点"的漏网情况。

## 5. 数值联动：三类内容的时间预算

一天 08:00–22:00 = 14 小时 = 28 个 30 分钟格。内容设计要按这个算：

| 用途 | 单次 | 一天上限 | 备注 |
|---|---|---|---|
| 训练 | 30 分钟 | 被她所在的地点和体力限制 | ¥120/次，EXP +3 |
| 制作人零工 | 30 分钟 | 体力限制 | ¥0–280 + 制作人属性 +3 |
| 闲聊 | 15 分钟 | **3 次** | 信任 +1 |
| 工作 | 替换她整天 | 每天最多 1 份/人 | 粉丝主要来源 |
| 专属行动 | 30 分钟 | 受作息窗口限制 | 信任 +5 |

**粉丝曲线**（验收基准）：第 7 天 800–1,200。达不到就说明工作数量不够或冷却太长。

## 7. 常见坑（全部是真实事故）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 同一份逻辑写两遍 | 通过的内容进不了游戏 | 抽成一个函数 + 一条两边一致的测试 |
| 运行时用 `import.meta.glob` | 构建后内容静默变空 | 生成文件（`content:sync`） |
| 给存档结构加字段没写迁移 | 老档白屏 | 升 `SAVE_VERSION` + 写迁移 + 一条迁移测试 |
| 用展示文案做判定 | flag 未满足被当成已满足 | 判定走 `checkCondition`，文案只用于显示 |
| 命令没生效却不提示 | 按钮像坏了 | 状态没变时写一条日志 |
| 事件被当成其他类型解析 | 体检报 `choices is not iterable` | 类型清单只有一份（`REVIEW_KINDS`） |
| 地点页按钮一多就挤 | 体验崩塌 | 一个入口 + 两级面板 |
| 专属行动比训练强 | 训练失去意义 | 专属行动给信任，训练给属性 |
| 变体条件用 `varAtLeast` 写分支 | 分支永远命中第一条（三选一永远显示第一种） | 精确匹配要同时写 `varAtLeast` + `varAtMost` |
| 重构视图对象字面量时丢字段 | 界面少一个标签，`tsc` 不报（可选字段） | 字段加进 `viewContract.test.ts` 的清单 |
| 测试断言没限定作用域 | 多偶像后 `getByText('尚未招募')` 命中 3 个，strict mode 报错 | 断言限定容器：`locator('.roster-card', { hasText })` |
| 用 shell 字符串替换改源码 | CRLF 导致替换静默不生效 | 改源码用编辑工具，见 [dev-guide](../current/dev-guide.md) |

## 8. 命名与编号

```text
草稿 id： draft.<kind>.<idol>.<block>.<slug>      draft.event.mano.b1.vocal
内容 id： <领域>.<idol>.<slug>                     evt.mano.after_vocal
```

## 10. 已知缺口（研究结论）

这一轮做完 B1–B6 + 系统层后，把流程里还靠人的地方列出来：

| # | 缺口 | 现状 | 方向 |
|---|---|---|---|
| 1 | 覆盖度靠人记 | ✅ 已做 `content:coverage`：按单元数一遍，缺什么直接列 | 可考虑接进 `content:validate` 变成硬门 |
| 0 | **不查语料就写** | 灯织的第一版就是靠印象写的，相遇写成公园长椅——和原作（练习室初见）完全不符 | 硬规则：**相遇、关键转折、核心台词必须有语料出处**，写进角色卡第 10 节 |
| 2 | 剧情链里的对话写在 TS，没走审查台 | ✅ 卡面章已改：对话进审查台，**过审后**才接入 STORY_CHAINS | 老的三条长线仍是 TS；改的时候照卡面章的做法 |
| 3 | 每个角色没有独立的 E2E | ⚠️ 靠 `tests/prologue/*` 手写 | 方向：按角色生成一个冒烟 spec（招募 → 训练 → 闲聊 → 工作） |
| 4 | 数值回归没有自动化 | ⚠️ `balance.test` 跑的是夹具包 | 方向：用正式包跑一个「第 7 天粉丝数」模拟脚本 |
| 5 | 打回的内容会落到「待修改」队列 | 已可见，但容易忘 | 每轮开始时先看「待修改」有没有积压 |
| 6 | **卡面地点与地图不匹配** | 卡面地点（海边、外地取景、具体店铺）地图上可能没有；整章在外地无法靠"加地点"解决 | 先记录。放量可能需要"临时场景"（只在该章存在、不进地图） |

第 2、3、4 条不做也不会立刻出错，但**换一个人来生产时最容易在这三处踩空**。
