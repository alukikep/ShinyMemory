# 地点与地区：评估稿（未实施）

> 问题：现在地点是**平铺的 9 个节点**。马上要加大学、剧场、电视台、商店……再平铺下去地图和检索都会失控。
> 你提的方向（"写个涩谷/秋叶原这样的街道，里面包含几个地点"）是对的，但**实现方式**有三种，代价差很多。
> 本文先评估，不动代码。

---

## 1. 现状（用数据说话）

`npm run content:where` 还不存在，这是临时统计的结果：

| 地点 | 行动 | 剧情链 | 日程里出现 | 备注 |
|---|---:|---:|---:|---|
| 事务所 | 4 | 9 | 3 | 相遇/汇报的枢纽 |
| 车站 | 2 | 1 | 0 | 交通枢纽，但只有 1 条链用 |
| 练习室 | 8 | 6 | 4 | 训练与事件的主要舞台 |
| 录音棚 | 4 | 3 | 4 | 有 6 份工作 |
| 家 | 3 | 1 | 0 | 只有 1 条链用 |
| 公园 | 4 | 6 | 4 | 高频 |
| 商业街 | 5 | 7 | 2 | 高频 |
| 学校 | 0 | 0 | 3 | **不可达**（`reachable: false`） |
| 泳池 | 0 | 1 | 0 | 只有巡的一张卡用；刚接进地图 |
| 医院 | 0 | 0 | 0 | 刚加，等霧子 |

三个观察：

1. **地点使用极不均匀**：学校/泳池/医院几乎没有"玩法内容"，但它们承担了**叙事地点**的职责。
2. **内容只认 `locationId`**：行动、事件、剧情步骤、角色日程、章节登记全都引用地点 id。
   改 id 或合并地点 = 全库改引用，风险最高。
3. **没有"这一带"的概念**：AI 写场景只知道 `locationId` + 一句 `description`，
   不知道"她从车站走过来要几分钟""商业街和事务所是不是同一片"。这就是你担心的检索问题。

## 2. 三种做法

| | A. 地区=数据分组 | B. 地区=导航层（地图先进地区） | C. 把地点并进地区 |
|---|---|---|---|
| 数据 | 加 `DistrictDef`，地点挂 `districtId` | 地区变成可进入的节点，地点成为子级 | 删掉泳池/医院等，合并成一个地区节点 |
| 玩家操作 | 不变（还是点地点） | 多一层点击：城市 → 地区 → 地点 | 少节点，但"泳池"不再是地点 |
| 内容改动 | 0（`locationId` 全部保留） | 0（引用仍是地点） | **大**：所有引用要改，章节/日程全部重登记 |
| 存档 | 不动（地区是派生数据） | 可能要动（当前所在层级） | 要动 |
| AI 检索 | 索引 + 命令即可 | 还要理解层级 | 地点细节丢失，反而更难写 |
| 工作量 | 半天 | 2–3 天 | 2 天，且长期维护成本最高 |
| 风险 | 低 | 中高（导航/存档/事件判定） | 高 |

**结论：用 A。** 地区是"描述与检索的分组层"，不是新的移动单位。
B 只在节点多到地图放不下时再做，而且应该是"地图上分组、点开看地点"，**不改变** `locationId` 语义。
C 直接排除：巡的泳池、霧子的医院都是**地点本身**有戏，合并等于把戏写丢。

## 3. A 方案的数据形状

```ts
// src/core/types.ts
export type DistrictDef = {
  id: string;          // 'bay' / 'shibuya'
  name: string;        // '海滨' / '涩谷'
  description: string; // 一句话：这一带是什么、气质如何
  color?: string;      // 地图分组底色
};

// LocationDef 增加一行
export type LocationDef = {
  ...
  districtId: string;  // 必填
};
```

索引里加三样（`src/core/contentIndexCore.ts`）：

```ts
districts: Map<string, DistrictDef>;
districtOfLocation: Map<string, DistrictDef>;
locationsByDistrict: Map<string, LocationDef[]>;
```

**不变式（写进校验，不靠记性）：**

- 内容（行动/事件/链/日程/章节）**只写 `locationId`**，永远不写 `districtId`；
- 地区只用于：地图分组、`content:where` 检索、文案里的"这一带"；
- 新地点必须有 `districtId`，地区必须有 ≥1 地点，名字不许重名。

## 5. AI 检索：写内容前应该能查到什么

这才是你问的核心。检索分三层，都实现成命令，AI 直接跑，不靠记忆：

### 5.1 `npm run content:where -- <id>`（地点/地区/偶像）

```text
$ npm run content:where -- hospital

地点  医院（hospital）
地区  海滨（bay）—— 公园、泳池、医院
描述  大学医院的中庭。长椅旁边有一小片花坛，风从走廊那头吹过来。
步行  从 事务所 过来：22 分钟（office → park → pool → hospital）
      从 车站 过来：打车 3 分钟 / 巴士 5 分钟
可做  （暂无行动）
出现  （暂无角色日程）
提示  霧子线会把这里当专属行动的舞台（规划中）
```

### 5.2 `npm run content:where -- --route <A> <B>`

```text
$ npm run content:where -- --route office hospital

路线  事务所（车站前）→ 公园（海滨）→ 泳池（海滨）→ 医院（海滨）
步行  22 分钟（8 + 14 + 8，跨地区）
```

写场景时的"她怎么过来的"一律以这个为准，不许凭印象写"马上到了"。

### 5.3 `npm run content:where -- --idol kiriko`

```text
现在  学校（文教区）· 08:00–15:00（protected）
之后  练习室（练习街区）· 15:00–18:00
晚上  医院（海滨）· 18:00–21:00
专属  医院 · 陪她照顾中庭的花坛（16:00–21:00）
地点  学校（不可达）/ 练习室 / 医院
```

### 5.4 写进文档的硬规则

| 规则 | 落在哪 |
|---|---|
| 场景里提到"在哪一带"时，用 `districtOfLocation` 的名称 | 写作手册 |
| 跨地区移动要写过渡句，分钟数取 `--route` | 写作手册 |
| 新角色接入先填"常去的地区/地点"，再写内容 | new-idol.md 第 3 步 |
| 内容引用永远 `locationId`；区 id 不进门 | 校验规则 |
