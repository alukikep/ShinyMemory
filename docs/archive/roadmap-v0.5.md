## 1. 当前基线

### 游戏定位

- 《偶像大师 闪耀色彩》同人生活模拟；
- Vite + React + TypeScript；
- 开放时间循环，以日程、训练、工作、事件、关系和金钱为核心；
- **正式设定没有结局**；
- 周付款/事务所维持费/债务暂不设计；
- 工作保持低负担：可接、可参与、可不参与，不设缺席惩罚。

### 已实现

- 日期、时间、体力、压力；
- 偶像属性 Rank + EXP、信任；
- 7 天日程和单日覆盖；
- 工作邀约、自动完成、可选参与；
- 事件触发、条件、效果、选项、事件链；
- 内容审查台：事件、工作、对话、剧情链的新建、编辑、批注、通过、打回、废弃、版本化；
- approved 内容加载和构建校验；
- 存档 v12 + 内容纪元 3；
- 176 个 Vitest 测试、11 条引擎 E2E、3 条内容 E2E、1 条正式序章 E2E、2 条审查 E2E。

### 当前内容量

- 正式事件 0；事件引擎保留，测试事件只存在于 fixture；
- 正式工作 0；工作系统保留；
- 正式商店/物品 0；物品系统保留；
- 8 个地点；
- 1 个正式偶像：樱木真乃；
- 7 个核心活动；
- 事务所自动序章 + 真乃公园两次相遇；
- Hiori/Meguru 只存在于 `content-fixture`，用于多偶像架构回归。

### 主要缺口

1. 正式内容只有真乃序章和相遇，招募后的日常内容仍为空；
2. 关系内容还没有开始填充；
3. 没有开放式中期目标；
4. 事件/工作/商店正式内容为零，内容密度不足；
5. 金钱暂时没有正式出口；
6. 美术、音频、移动端表现尚未进入正式阶段。

## 2. 设计原则

1. **不为了加系统而加系统**：先验证现有循环，再决定是否扩架构。
2. **低压力的偶像生活**：工作可选，不用缺席惩罚制造负担。
3. **没有结局不等于没有目标**：用关系、职业里程碑、收集和自我目标提供方向。
4. **钱买选择，不买胜利**：金钱用于内容、机会、恢复和关系，不直接买数值最优解。
5. **不新增货币和状态条**：优先使用现有体力、压力、信任、Rank、金钱。
6. **内容优先于系统**：如果加内容能验证方向，就不先造通用系统。
7. **审查流程**：
   - 事件/工作/对话/剧情链走审查台；
   - 活动、物品目前是静态 TS，属于已接受的手工审查例外；
   - 内容量变大后再考虑扩展 `ReviewKind`。
8. **每个阶段有验收标准**：没有验收标准的内容不进入路线图。

## 3. 优先级总览

| 优先级 | 事项 | 原因 |
|---|---|---|
| P0 | 试玩校准现有经济与日常循环 | 刚加入商店/礼物/课程/餐费，尚未验证 |
| P1 | 角色相遇与剧情链 | 先解决“偶像从哪来、怎么认识、怎么招募” |
| P2 | 关系循环 | 角色进入名单后，才谈得上长期关系内容 |
| P3 | 开放式职业目标 | 给玩家中期方向，不依赖结局和周付款 |
| P4 | 内容密度 | 防止两周后重复感过强 |
| P5 | 表现、美术、音频、发布 | 循环成立后再投入 |
| 延后 | 周付款/债务/事务所考核 | 已明确暂不设计 |
| 延后 | 新偶像、装备系统、复杂商店 | 先让现有内容成立 |

## 4. 阶段路线图

状态说明：

- `planned`：已列入，未开始；
- `in progress`：正在做；
- `done`：已完成并验收；
- `paused`：暂缓；
- `cut`：取消。

| 阶段 | 状态 | 预计 | 目标 | 验收 |
|---|---|---|---|---|
| 0. 试玩校准 | planned | 2–3 天 | 验证现有钱、压力、工作、商店是否成立 | 一周至少 2 次有意义消费；钱有一次低于 2000；没有唯一最优循环 |

| 2. 关系循环 | planned | 5–7 天 | 让关系进入主循环 | 玩家为关系安排时间；关系能恢复压力并解锁内容 |

## 5. 阶段详情

### 阶段 0：试玩校准

**目标**

不写新系统，先验证当前循环是否值得继续扩展。

**工作**

- 连续玩 7–14 个游戏日；
- 记录每天的行动、金钱、压力、工作、礼物、课程、餐费；
- 观察是否出现“不知道干什么”；
- 观察是否出现“只有一种最优玩法”；
- 调整课程价格、餐费、礼物价格、工作收入和压力变化；
- 记录重复事件。

**验收**

```text
一周至少 2 次有意义的消费决策
钱至少有一次低于 2000
没有“每天固定训练→工作”的唯一解
压力至少触发过一次恢复决策
没有因为价格过高而完全不用某类内容
```

**输出**

- 一份试玩记录；
- 一张数值调整清单；
- 不新增系统。

### 阶段 1：角色相遇与剧情链

**设计稿**

[灯织相遇事件：垂直切片与架构设计](superpowers/specs/2026-10-27-hiori-encounter-design.md)（草案，待评审）

**当前进度**

正式内容已重置为真乃单偶像：

- 新游戏自动播放事务所序章；
- 真乃初始 unknown，开局没有已招募偶像；
- 属性区空状态，地图/移动/休息/自由行动/NPC 可用；
- 公园两次低提示相遇：循着歌声 → 再次听见歌声；
- 第一次 known，第二次 recruited；
- 独立对话 overlay、剧情链状态、known/recruited 过滤；
- v12 存档迁移 + 内容纪元 3；
- 对话/剧情结构、引用、可达性和 terminal 校验，并接入构建；
- 审查台支持对话/剧情链草稿、审批和 approved 载入；
- 多剧情链 priority；
- 活动目标规则：地点页无对象行动，偶像页 present-idol 行动；
- 自由时间已移到偶像互动页；
- 初始偶像状态由内容配置驱动；
- 冻结 `content-fixture` 内容包 + 全局测试 setup，单元测试不再依赖正式内容；
- Playwright 引擎/内容套件拆分，fixture build；
- 正式序章/真乃 E2E；
- 招募后训练 E2E；
- 176 个单元测试、Hiori/Meguru fixture 回归、移动端检查。

仍未做：

- 正式事件、工作、商店/物品内容；
- 真乃招募后的日常/关系内容；
- 正式设定下的第二名偶像；
- 更多相遇地点和分支内容。

**目标**

让偶像不是一开始就全部出现在名册里，而是通过地点剧情链逐渐被玩家认识、招募，再进入日常养成。

**需求**

1. 增加可承载长对话的节点，像 Galgame 一样连续推进文本和选择；
2. 选项不产生结果分支，只决定下一段对话和属性/好感奖励；
3. 偶像名册只显示已经认识或招募的偶像；
4. 未认识/未招募的偶像没有日程表；
5. 在指定地点触发剧情链，按天数间隔推进，直到认识并招募。

**建议的最小垂直切片**

先不要做完整剧情引擎，只做一个偶像：

```text
初始：真乃已招募，灯织未知
第 1 天：公园第一次遇见灯织
→ 长对话，若干选择
→ 记录“已认识”，但仍未招募
第 3 天：公园第二次遇见
→ 继续剧情对话
→ 选择是否招募
→ 招募后进入名册、显示日程、可训练
```

**初步数据模型**

```ts
type IdolStatus = 'unknown' | 'known' | 'recruited';

type DialogueNode = {
  id: string;
  speakerId?: string;
  text: string;
  choices?: DialogueChoice[];
  nextNodeId?: string;
};

type DialogueChoice = {
  label: string;
  nextNodeId: string;
  effects?: Effect[];
  requires?: Condition[];
};

type StoryChainStep = {
  id: string;
  locationId: string;
  dayOffset?: number;
  requires?: Condition[];
  dialogueId: string;
};

type StoryChainDef = {
  id: string;
  idolId: string;
  steps: StoryChainStep[];
};
```

状态侧至少需要：

```text
IdolState.status
GameState.storyChains
GameState.pendingDialogueId
GameState.dialogueNodeId
```

**架构判断**

这不是纯内容功能，至少需要：

- 对话节点引擎；
- 对话 UI（文本推进、选项、保存/恢复）；
- 剧情链状态与触发；
- 偶像状态过滤；
- 名册/日程/场景行动过滤；
- 存档迁移。

**验收**

```text
新游戏时灯织不在名册
公园第一次遇见触发长对话
两天后在公园触发第二次剧情
选择能影响信任/好感
招募后灯织进入名册
招募后才显示日程
读档后剧情步骤不丢失、不重复
```

### 阶段 2：关系循环

**目标**

让关系成为玩家安排时间的原因，而不是只显示 Rank。

**工作**

每个偶像先做 3 个信任门槛场景：

```text
信任 E：日常对话
信任 D：共同外出
信任 C：更深入的个人事件
```

同时：

- 礼物送出后的后续反应；
- 1 个可主动安排的外出活动；
- 高信任时提供压力恢复；
- 关系事件解锁新的工作、对话或地点内容；
- 关系内容优先走事件审查流程。

**验收**

```text
玩家会为了某个偶像安排某一天
关系不只是数值，而是能解锁场景
关系能影响压力、工作或日常选择
```

**建议先做**

- 真乃和灯织各 1 个信任 D 场景；
- 1 个共同外出活动；
- 1 个礼物后续事件。

### 阶段 3：开放式职业目标

**目标**

在没有结局、没有周付款的前提下，给玩家中期方向。

**工作**

- 工作等级/解锁条件；
- 2–3 种新工作类型；
- 粉丝信/评价；
- 排名里程碑；
- 工作室升级；
- 工作板每周刷新；
- 可选的制作人手账目标。

制作人手账示例：

```text
本周想做的事：
□ 存到 8000
□ 和真乃去一次咖啡店
□ 完成一次电台工作
□ 把表现练到 C
```

完成给内容或小奖励，不完成没有惩罚。

**验收**

```text
玩家打开游戏时知道自己这周想做什么
工作不是随机奖励，而是职业路径
钱能推动职业目标
```

### 阶段 4：内容密度

**目标**

降低长时间游玩后的重复感。

**工作**

- 2–3 种新工作；
- 15–20 个新事件；
- 3–5 条事件链；
- 1 个新场景；
- 地点专属事件；
- 同一事件按压力/信任/排名变体；
- 事件链优先于单发事件。

**验收**

```text
连续两周不大量重复同一文本
每个地点有辨识度
玩家能说出至少 3 个记得的事件
```

---

### 阶段 5：表现与发布

**目标**

从“能玩的原型”走向“可以展示的版本”。

**工作**

- Q 版头像/立绘；
- 场景背景；
- BGM/音效；
- 移动端细节；
- 可访问性；
- 存档/性能；
- 审查页扩展到活动/物品（如果内容量需要）。

**验收**

```text
新玩家无需 debug 即可完整体验
移动端无横向溢出
没有影响主循环的存档/性能问题
```

## 6. 角色相遇与剧情链方案评估

### 结论

方向正确，而且优先级应该高于“关系循环”。

原因：

- 现在所有偶像默认都在名册里，未招募也没有边界；
- 玩家缺少“认识她”的过程，角色关系像是直接开始；
- 长对话和剧情链能把地点、时间、选择和角色招募连成一个完整的小循环。

但它**不是纯内容功能**，至少涉及三个系统：

```text
对话节点与对话 UI
剧情链状态与触发
偶像生命周期（未知/认识/招募）
```

### 当前架构能支持到什么程度

| 能力 | 现状 | 判断 |
|---|---|---|
| 单段事件文本 | 已有 | 可直接用 |
| 事件选项和效果 | 已有 | 可复用 |
| 事件链 `nextEventId` | 已有 | 能链，但每段会回到事件结果页，不像连续 Galgame |
| 相对天数触发 | 不完整 | 目前只有固定 `dayAtLeast` / 冷却，不能可靠表达“遇见后第 2 天” |
| 长对话节点 | 没有 | 需要新的 `DialogueNode` 和对话 UI |
| 对话历史/连续推进 | 没有 | 需要 UI 状态 |
| 偶像未知/认识/招募 | 没有 | `IdolState` 目前只有 `id` + `stats` |
| 名册过滤 | 没有 | [IdolRoster.tsx](src/ui/components/IdolRoster.tsx) 直接显示全部 `state.idols` |
| 日程过滤 | 没有 | [IdolSchedule.tsx](src/ui/components/IdolSchedule.tsx) 显示全部偶像 |
| 招募前隐藏日程 | 没有 | `IdolDef.schedule` 始终存在，需要在 UI/场景层过滤 |
| 存档迁移 | 有基础 | 需要新增对话/剧情链字段并升级版本 |

### 建议的技术边界

#### 对话节点

不要把“长对话”硬塞进一个 `EventDef`。

当前事件流程是：

```text
事件文本
→ 选择
→ 事件结果页
→ 继续
→ 下一个事件
```

这适合单次事件，不适合连续对话。建议新增：

```ts
type DialogueNode = {
  id: string;
  speakerId?: string;
  text: string;
  choices?: DialogueChoice[];
  nextNodeId?: string;
};

type DialogueChoice = {
  label: string;
  nextNodeId: string;
  effects?: Effect[];
  requires?: Condition[];
};
```

状态：

```text
pendingDialogueId
dialogueNodeId
```

UI 需要：

- 点击推进文本；
- 选项；
- 说话人/头像；
- 保存和恢复；
- 可选：历史记录、跳过。

#### 剧情链

不建议只用 flag 拼“两天后再来”。

建议显式保存：

```ts
type StoryChainState = {
  chainId: string;
  stepIndex: number;
  nextEligibleDay?: number;
  completed?: boolean;
};
```

触发方式建议：

```text
到达指定地点 + 当前天数满足 + 剧情步骤匹配
→ 主栏位出现“遇见/继续剧情”行动
→ 进入对话
→ 对话结束推进步骤
```

这样比随机事件可靠，玩家也不会因为随机没触发而错过剧情。

#### 偶像生命周期

建议：

```ts
type IdolStatus = 'unknown' | 'known' | 'recruited';
```

规则：

```text
unknown：名册不显示、无日程、场景不出现
known：名册可显示，但无日程、不能训练/工作
recruited：完整名册、日程、训练、工作、礼物
```

**需要特别决定初始偶像。**

当前游戏默认真乃是 active idol，训练、工作、属性面板都依赖 `activeIdolId`。  
如果所有偶像都从未知开始，会牵连开场流程和大量空状态。

建议第一版：

```text
真乃：初始已招募
灯织：未知，通过公园剧情链招募
```

这样能保留当前循环，又能验证完整的“遇见 → 认识 → 招募”流程。

### 审查流程问题

当前审查页只支持：

```text
event
job
```

对话节点和剧情链是新内容类型，默认不会进入审查页。

三个选项：

1. 垂直切片先写静态 TS，接受手工审查；
2. 把对话节点包装成事件，复用现有审查；
3. 扩展 `ReviewKind` 到 `dialogue` / `story`。

我的建议：

```text
先用方案 1 验证体验
→ 如果剧情链确定保留
→ 再扩展审查页
```

不要在验证剧情体验之前先造一套剧情编辑器。

### 范围估计

单偶像垂直切片：

| 工作 | 估计 |
|---|---|
| 偶像状态、名册/日程/场景过滤 | 2–3 天 |
| 对话节点引擎 + UI + 存档 | 4–6 天 |
| 剧情链状态 + 地点触发 + 天数间隔 | 3–5 天 |
| 一个偶像的完整相遇/招募内容 | 4–6 天 |
| 测试、迁移、验收 | 2–3 天 |

合计约 **3–4 周**。  
如果改用现有事件链、不做连续对话 UI，可以压缩到 **1–2 周**，但达不到“Galgame 长对话”的体验目标。

### 主要风险

1. **范围蔓延**：对话、剧情链、偶像生命周期三套系统一起上，容易做不完。
2. **初始偶像空状态**：全部未知会破坏当前 active idol 流程。
3. **日程泄露**：只过滤名册不够，场景 actor、hero、日程、训练入口都要过滤。
4. **剧情错过**：随机触发或时间窗太窄会让玩家错过；建议用地点行动而不是随机事件。
5. **存档中断**：必须支持对话中途保存和读档恢复。
6. **选择变假**：没有结果分支时，选择至少要在下一段文本、信任/好感、后续对话上有可感知差异。
7. **内容审查缺口**：已接入对话/剧情链审查；活动/物品仍为静态 TS 例外。
8. **文本量**：长对话会显著增加写作量，建议每节点 2–4 句，先做 15–25 个节点。

### 推荐决策

```text
1. 先做单偶像垂直切片（灯织）
2. 真乃保持初始已招募
3. 灯织：未知 → 公园第一次遇见 → 两天后第二次 → 招募
4. 名册显示 known + recruited；日程只显示 recruited
5. 对话节点独立于事件系统
6. 剧情链显式状态，不用纯 flag
7. 对话/剧情链已接入审查；approved 内容进入构建
8. 已完成 Hiori/Meguru 两条测试切片；正式内容仍需替换
```
