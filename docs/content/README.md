> 这里放**内容素材与生产计划**：角色卡、块清单、进度。
> 数值标准在 [`docs/current/content-standards.md`](../current/content-standards.md)。
> 审查流程在 [`docs/systems/content-review.md`](../systems/content-review.md)。
> 角色语气以 **官方剧情中译语料库** 为准，见各角色卡第 12 节。

## 1. 目录

```text
docs/content/
  README.md              本文件：流程 + 块清单 + 进度
  mano/
    character.md         真乃的角色卡（写作时逐条对照）
```

一个角色一个目录。第二个偶像上线时新建 `docs/content/<idol>/`。

## 2. 生产单位：一个块

**一个块 = 一个归属 × 一个挂载点 × 一种内容单元。**

例：「真乃 · 训练后 · 事件」是一个块。「真乃 · 偶像页 · 行动」是另一个块。两者不重叠，各自验收。

不用「日常 / 严肃 / 温馨」这种分法——不可验证，而且同一条内容能同时属于两类，最后会重复生产或漏掉。

| 轴 | 取值 |
|---|---|
| 归属 | 单个偶像 / 全员通用 / 制作人 / 地点 / 系统 |
| 挂载点 | 偶像页 / 地点页 / 行动后 / 到达 / 定时 / 延迟 / 剧情链步骤 / NPC 话题 |
| 单元 | 行动 / 事件 / 对话 / 剧情链 / 工作 / 物品·商店 / 话题 |

## 3. 一个块的流程

```text
1. 定坐标      写进本文件的块表
2. 查角色卡    语气、称呼、阶段态度、OOC 对照
3. 查数值档位  时长 / 体力 / 钱 / EXP / 粉丝
4. 写草稿      npm run review → 新建（id 带块号）
5. 过审查台    预览 → 批注 → 打回 → 改 → 通过
6. 进游戏玩    npm run build → 真的触发一次
7. 记状态      块表标记完成，写一句"学到了什么"
```

第 6 步不能省。只在审查台看预览，看不出时序、抢占、排版。

## 4. 命名

草稿 id 带块号，审查台队列本身就是进度表：

```text
draft.event.mano.b1.vocal
draft.event.mano.b1.dance
draft.activity.mano.b3.extra_practice
draft.dialogue.mano.b2.step3
```

内容 id 用领域前缀，不用块号（块号是生产期的，不该泄漏到内容里）：

```text
evt.mano.after_vocal      ✅
evt.mano.b1_after_vocal   ❌
```

## 5. 完成的标准（DoD）

一个块算完成，要同时满足：

- [ ] 条数在 3–8 之间
- [ ] 每条都过了 `npm run content:validate`
- [ ] 每条都对照过角色卡的 10 条自查
- [ ] 至少一条选项「有代价」
- [ ] 在游戏里真的触发过一次（不是审查台预览）
- [ ] 没有新增未使用的 flag / var
- [ ] 块表标记完成

## 7. 一块写完记什么

在块表下面追加一行短记录，只写三点：

```text
B1 2026-10-30  5 条 / 通过 4 条 / 打回 1 条（声音太活泼）
   学到：她"惊讶"不能写成"惊喜"，用ほわっ带一下就够
```

三段：块号日期、数量、一条经验。经验积累到 3 条以上，回填进角色卡的 OOC 对照表。

```text
B1 2026-10-29  5 条 / 通过 5 / 打回 0
   学到：
   · `after` + `afterIdol` 只对偶像页的行动生效；地点页行动（环顾）没有偶像上下文，
     要用 `castPresent` 代替，这是两种不同的锚定方式，块里要写清楚。
   · 审查台流转后会离开当前队列，需要按 tab 重新选中——已改成"停在当前队列、自动选下一条"。
   · 事件没有文本变体，重复触发会一字不差；高频锚点应该写多条 `once`，而不是一条循环。
```
