# 卡面改编执行手册

> 从"看到一张卡"到"通过审查"的完整顺序。
> 每一步都标注了**哪条命令会拦住你**——规则不靠记性，靠构建。
>
> 相关：写作规范在 [playbook.md](playbook.md)，开发约定在 [dev-guide](../current/dev-guide.md)。

---

## 0. 先看清素材（最容易出错的一步）

```bash
npm run content:card -- "data/story/八宮めぐる/【夏に恋するピチカート！】八宮めぐる"
```

输出按 **commu 序号**排好，每段带行数和开头两句。要确认四件事：

| 确认什么 | 怎么看 |
|---|---|
| 这张卡一共几段 | 输出的条数（2–5 段很常见） |
| 游戏内顺序 | `[01] [02] [03]…` 的序号 |
| 哪几段是前后篇 | 读内容：接得上的会共享场景/话题 |
| 每段有没有选项 | 看原文，别猜 |

**这一条是血泪**：曾经只 `ls` 到两个文件就当成全部（实际 5 段），还把第 4 段当成了第 2 段。

---

## 1. 读原文，判断"选项有没有分支"

原作里，选项有两种形态：

| 形态 | 特征 | 例子 |
|---|---|---|
| **选完就合流** | 选项本身是那句台词，下一句立刻回主线 | 純白、咖啡 |
| **选项后有大段分支** | 选中的那句会被**重复显示**，之后各走一段再合流 | 泳装 |

判断依据：**选项块之后的第一句，是不是等于其中某个选项**。

```text
选项块：看起来精神 / 试试搭配 / 交给运气
下一句：看起来精神的会不会更适合你   ← 重复了选项 → 有分支
```

`content:anchors` 会自动做这个判断（`expectBranch`），然后按不同标准校验：

- 有分支 → **每条分支至少 3 个节点**
- 无分支 → 不要求（1 句也合法）

---

## 2. 定章节边界

| 单位 | 规则 |
|---|---|
| **一段 commu = 一章** | 不要合并，也不要拆分 |
| **一章 = 1 步剧情链** | 一次坐下读完；跨天的章才用多步 + 节奏 |
| 一章 = **1 段对话** | 选项的影响必须贯穿整章剩余部分 |

**为什么一章必须是一段对话**：把一章拆成几步，选项就只能影响那一步，
后面的步骤照旧——这在视觉小说里不成立。

---

## 3. 写对话：结构固定

```text
桥段开头（怎么进入这一幕，1–2 句）
  ↓
原文正文（压缩后的原句）
  ↓
原作的选项（0 或 1 个，位置不动）
  ↓
选项之后的分支正文（原作有就写，长度按原作）
  ↓
落点（原卡常常停在半路，必须补一句结束）
```

**不要**在桥段里加选项、不要在章中加第二个选择点。

---

## 4. 登记两件事

**① 章节链**（`src/core/content/chapters/<名字>.ts`）

```ts
{
  id: 'meguru-swimsuit',
  title: '泳装的颜色',
  revealWhen: [...],          // 触发条件
  steps: [{
    locationId: 'shopping_street',
    timeWindow: { fromMinute: 10*60, toMinute: 20*60 },
    dialogueId: 'dialogue.meguru.swimsuit',
    actionLabel: '杂志那边约了新人特集',
    when: [...],              // 最早天数等
    effects: [                // 章末结算一次，量要小
      { kind: 'attributeExp', ref: 'trust', tier: 3 },
      { kind: 'sharedStat', stat: 'stress', delta: -5 },
      { kind: 'flag', key: 'completed.meguru.swimsuit', value: true },
    ],
  }],
}
```

**② 出处表**（`src/core/content/chapterSources.ts`）

```ts
{
  chapterId: 'meguru-swimsuit',
  source: 'data/story/…/カラフルサマー.csv',
  card: { title: '夏に恋するピチカート！', index: 1, total: 5 },
  anchors: ['能全部都穿到就好了——！', … ≥3 句逐字原文],
}
```

`card.index / total` 会被**重新计算**后比对，填错直接红。

---

## 5. 送审与接入

```text
对话先进审查台（5 章 = 5 条草稿，一章一组）
  ↓ 整章通过
把章节链接进 STORY_CHAINS
  ↓
取消对应 E2E 的 skip，跑真实流程
```

**顺序不能反**：先接链会让 `BASE_PACK` 引用不存在的对话，每个草稿预检都报 `dialogue-ref`。

## 6. 提交前跑这几条

```bash
npm run content:anchors   # 锚点、卡内节号、章节形状
npm run content:audit     # 结构/数值体检
npm test                  # 单元测试
npm run build             # 类型 + 门禁 + 打包
```

| 会拦住你的规则 | 拦什么 |
|---|---|
| 锚点不足 3 句 / 在语料里找不到 / 没进游戏 | 凭印象写、压缩时删掉原句 |
| 卡内节号与语料不一致 | 手填顺序填错 |
| 卡面章不是 1 步 | 又把一章拆成几步 |
| 一章多于 1 个选择点 | 自己加戏 |
| 分支只有 1 个节点（原作有分支时） | 选项变成"只换一句话" |
| 分支没有汇合点 | 走丢，回不到主线 |

---

## 7. 踩过的坑（全部真实发生）

| # | 事故 | 现在的防线 |
|---|---|---|
| 1 | 没查语料就写，相遇写成公园长椅 | 角色卡要求 3 条逐字引文 |
| 2 | 一张卡只看到 2 个文件（实际 5 段） | `content:card` 工具 |
| 3 | 把第 4 段当成第 2 段 | commu id 序号 + 节号校验 |
| 4 | 一章拆 4 步，选项只影响一步 | 一章 = 1 步 = 1 段对话 |
| 5 | 分支压成 1 句，选项形同虚设 | `expectBranch` + 分支厚度校验 |
| 6 | 自作主张给桥段加选项（9 个 vs 原作 3 个） | 一章 ≤ 1 个选择点 |
| 7 | 奖励给太多（信任 +13/章） | 章末结算一次，总量 ≤ 信任 4 |

---

## 8. 一句话总结

**素材按序号读全 → 一章一段对话 → 选项数量跟着原作 → 分支按原作的厚度 → 锚点逐字保留 → 先过审再接入。**
