# 架构完善实施计划

> 2026-11-04 · 计划阶段，尚未实施本计划中的重构。已有内容档案、审查台页面、每日邀约和剧情容量功能继续作为基线。

## 1. 目标与事实

目标是降低新增机制、内容生产和审查集成的维护成本。按 A → B1 → B2 的顺序推进；C 单独形成运行时批次，D 在需要安排实际内容生产时再启动。

本次核对的事实：

- `ContentInventoryPanel.tsx` 通过 `import type` 引用工具层 `loadInventory` 并推导返回类型。不会因此把 Node 文件读取带入浏览器运行时，但展示层的数据契约依赖工具实现。
- `tools/contentInventory.ts` 同时负责文件读取、装配、快照比较、报告加载、参数解析和格式化；审查 API 复用该模块，统计没有重复实现，但职责可以进一步分开。
- `productionPack.ts` 与档案均使用 `mergeApprovedContent`、`attachPendingChapters`；`contentCoverage.ts` 仍手写章节挂载，`chapterBoard.ts` 根据合并包中的对话可用性统计章节。
- 覆盖率按话题前缀、bond 行动和到达事件计数，与档案的宿主、显式偶像归属及审批/接入双维度有差异。覆盖率最低要求和内容产量不是同一种指标。
- `jobInvitations.ts`、`storyCapacity.ts` 已有规则模块；`sim.ts` 仍负责工作接取与剧情评估等流程。拆分范围应由重复判断和依赖决定，不能只按文件行数决定。

本计划不改变审批权：通过与打回仍由人执行。保留当前工作区已有改动，各阶段独立验收；历史测试结果不代表新版本已验证。

## 2. A：明确内容档案契约（首个实施批次）

交付：让统计内核、文件服务、CLI 和审查页面依赖共同的数据定义。

1. 拟建 `src/shared/contentInventoryTypes.ts`，明确报告、条目、版本、关系、卡面统计及警告类型；包含现有 schemaVersion 和审批/接入字段。该模块仅包含类型，不依赖 Node、React、工具或游戏初始化。
2. 为统计内核与加载服务声明返回类型，页面直接引用共享报告类型；删除页面对工具函数返回类型的推导。
3. 拟建 `tools/contentInventoryService.ts`，承接读取源文件、装配与快照比较；CLI 保留参数、筛选、展示和进程出口；reviewPlugin 直接调用服务。统计纯函数仍留在 core，不改算法。
4. 核对 JSON 与 UI 原有字段、筛选及错误语义保持一致；不要将“结构内容”改成“已批准”，不要将“源包接入”改成“已部署”。

验收：

- 同一输入的完整报告迁移前后相等，含排序、警告、历史数量、修订与出处；使用测试比较完整结构，不仅比较汇总数。
- CLI 错误参数退出码、纯 JSON、未知偶像及读盘失败行为保持；接口失败仍能在页面重试。
- 共享类型不反向引用 tools；页面没有 Node/工具层导入，建立针对这些明确边界的检查，并接入已有测试入口。
- 相关统计/CLI 测试、类型检查、构建，以及审查台 inventory 单条 E2E。无运行时和存档变化，不为此批启动正式游戏全量 E2E。

## 3. B1：统一装配与诊断，保持统计政策

交付：各消费端复用同一装配过程，同时获得足够的诊断信息。

- 基于现有 merge 与 attach 提取可注入的纯装配入口，接收基础包、批准内容与章节登记；返回合并包、挂载后包、重复 id 和缺失依赖等诊断。保留现有导出或提供兼容包装，逐个迁移消费者。
- 游戏继续使用生成快照，工具使用文件系统中的批准源；两者经过相同纯装配逻辑。来源不同必须显式保留，不能让浏览器读文件系统，工具也不能偷偷 sync。
- 看板分别展示“对话可用”和“整链接入”。覆盖率先仅替换重复装配，不同时更改计数方法和最低门槛。
- 迁移前记录固定样例下的内容 id、链 id、重复项和缺失项；迁移后逐项比较。真实数据只作为补充核对，边界靠固定样例验证。

验收：部分批准、全部批准、重复 id、缺对话、未知话题宿主、空登记，以及当前正式包和 fixture 包的行为明确；不静默丢弃诊断。执行相关测试与基础检查。因涉及共享内容装配，记录批次收尾须对稳定最终版本跑完整正式 E2E；fixture/审查配置按实际影响补测，不逐个消费者跑全量。

## 4. B2：统一归属事实，独立迁移覆盖率政策

交付分两步，不能合并成一次未经核对的门禁调整：

1. 提取纯关联分析，返回偶像、关系与字段路径，供档案和诊断复用。覆盖率仍可使用自己的“训练可用性”等政策；例如通用训练可满足训练覆盖，但不能变成每人专属产量。一卡/多章、宿主话题键、旧版/修订、通用/参与/条件关联分别保留。
2. 先产生旧/新口径差异报告，按角色与内容 id 说明差异。核对原始字段后再决定事件覆盖指标与门槛；欠缺内容登记为缺口，不为过门禁自动降低要求、补写内容或自动批准。

验收：到达入口和 activity selector 不误作偶像归属；未知归属可见；对话参与与主属可重叠但各自去重；读取错误不是零内容。对明确差异建立固定回归案例。报告阶段不影响构建是否通过；政策切换另列变更说明、前后基线与测试范围。

## 5. C：按业务边界整理运行时（后续独立批次）

先处理工作接取资格，再评估剧情启动资格；每个领域单独复查，不同时搬迁整个 sim。

- 工作：盘点 scene 与命令端判断，拟提取无副作用的资格评估，返回允许/拒绝及结构化原因。显式区分“邀约可展示”“某偶像可接取”“当前地点与阶段允许执行”，保留各自上下文。
- 剧情：以已有容量模块为基础，统一新链启动资格与拒绝原因。进行中续推、招募豁免、同偶像限制、全局容量及旧档超额处理保持现状。
- sim 保留状态变更与效果执行，界面投影使用评估结果；依赖通过参数传入，避免新模块反向导入 sim 导致循环。
- 不顺带修改时间、结算、随机序列或存档形状。若发现必须改变行为，拆成明确功能任务并补迁移设计。

验收以行为断言为主：按钮与命令一致、直接命令无法绕过门槛、拒绝不修改状态、正确接取的日程与工作同时写入、剧情结束释放容量。相关状态测试与单条 E2E先通过；涉及共享调度的最终批次再执行正式全量。

## 6. D：生产计划登记（按需求启动）

需要实际分派内容批次时，再设计轻量结构化登记：稳定任务 id、目标偶像、内容类型、目标范围、负责人、计划状态、关联内容键/草稿 lineage 和人工验收记录。

计划状态与审批状态分开；计划不直接计入已生产数量，审批后关联实际条目，不复制内容 payload 和手工计数。先提供读取与校验，再按使用情况决定是否增加编辑页面。当前不创建内容任务，不指定模型或自动启动生产。
