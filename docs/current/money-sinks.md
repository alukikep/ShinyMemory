## 2. 商店：冷却 + 永久限购（D2 / D8）

### 2.1 三种购买状态

| 状态 | 判定 | UI |
|---|---|---|
| 可购买 | 未售罄且不在冷却 | 「购买」 |
| 冷却中 | `now < last + cooldownMinutes` | 「冷却中 · 还需 X 小时/分钟」 |
| 永久售罄 | `shopPurchases >= maxPurchases` | 「已售罄」 |

规则：

- `cooldownMinutes?: number`：购买后到下次可买的**游戏内分钟数**；
- `maxPurchases?: number`：**保留**，表示永久限购（成长道具、功能道具）；
- 两者可以同时存在：先判永久上限，再判冷却；
- `shopPurchases` 继续记录累计购买次数（永久限购用）；
- `shopCooldowns[itemId]` 记录上次购买的绝对分钟（冷却用）；
- 冷却按游戏内时间走：睡觉、跨天、读档都照常推进。

### 2.2 存档

```text
SAVE_VERSION 18 → 19
迁移：state.shopCooldowns ??= {}
```

旧的 `maxPurchases` 存档继续生效；新加的冷却只影响有 `cooldownMinutes` 的商品。

### 2.3 UI

- 冷却中显示剩余时间，按钮禁用；
- 永久售罄显示「已售罄」，不再显示倒计时；
- 永久限购商品在购买前给一句明确提示：「购买后不可再买」；
- 同一件商品不要同时显示「已购 X/Y」和「冷却中」，避免两个门槛互相盖住。

### 2.4 建议配置

| 物品 | 价格 | 模式 | 数值 |
|---|---:|---|---|
| 信纸 | ¥200 | 冷却 | 24 小时 |
| 花束 | ¥500 | 冷却 | 24 小时 |
| 演唱会照片 | ¥300 | 冷却 | 24 小时 |
| 小鸟挂饰 | ¥600 | 冷却 | 72 小时 |
| 发饰 | ¥800 | 冷却 | 72 小时 |
| 成长道具（以后） | 待定 | 永久限购 | `maxPurchases: 1` |
| 事务所汽车（以后） | 待定 | 永久限购 | `maxPurchases: 1` |

- 24 小时是“每天一次”的日常节奏；72 小时是“隔几天一次”的强礼物。
- 永久限购用于“买一次就改变玩法”的东西，不参与日常刷取。
- 更长冷却（168 小时等）留给更强的功能道具；先不做内容。

### 2.5 可行性与可玩性

**可行性：高。** `cooldownMinutes` 是新字段，`maxPurchases` 已经存在；改动集中在 `types.ts` / `sim.ts` / `ShopModal.tsx` / `save.ts` / 内容 JSON / 测试，约 1–2 天。

**可玩性：高。** 24 小时礼物形成日常仪式，72 小时礼物形成“攒着送”的期待，永久限购形成长期目标。三者是不同节奏，不是同一种等待。

**风险与缓解**：

- **等待感**：冷却按游戏内时间，睡一觉就能推进；UI 必须显示倒计时。
- **状态混淆**：永久售罄和冷却中要分开显示；否则玩家不知道是“等”还是“永远没了”。
- **永久道具的平衡**：成长/功能道具不能变成“买完游戏结束”。价格要高、效果要偏 QoL（如免费快速旅行），不要直接卖 EXP/Fans。
- **旧内容迁移**：现有 5 件物品要从 `maxPurchases` 改成 `cooldownMinutes`，但字段保留，旧存档不会因为字段消失而报错。

## 3. 设施升级：替换选项（D3 / D4 / D6 / D7）

### 3.0 三个房间与设施管理室

**三个独立房间**：声乐室、舞蹈室、表现室，各自一条等级线，互不影响。

```text
facility.vocal       → vocal 的等级
facility.dance       → dance 的等级
facility.expression  → expression 的等级
```

- 每个房间 0–2 级（后续可扩），升级只替换该房间的训练选项；
- 玩家可以只升声乐，不升舞蹈；钱要花在“现在最需要的那条线”上；
- 三个房间都挂在 `practice_room`，入口统一。

**入口**：练习室场景里增加「设施管理室」条目，进入后打开设施面板。

面板内容：

```text
声乐室    初级 → 中级    ¥5,000    50 分钟 / EXP +3
舞蹈室    初级 → 中级    ¥5,000    50 分钟 / EXP +3
表现室    初级 → 中级    ¥5,000    50 分钟 / EXP +3
```

- 当前等级、下一级费用、升级后的变化，一行一个房间；
- 费用已定：5,000 / 10,000 / 15,000；数值见 3.4；
- 升级不消耗时间（和购买/赠送一致）；如果以后想要“施工期”，用 `scheduleEvent` 加延迟。

**入口实现选型**：

| 方案 | 做法 | 成本 | 结论 |
|---|---|---|---|
| A（推荐 v1） | `practice_room` 场景加一个「设施管理室」条目，打开面板 | 低，不新增地点 | 先做 |
| B（以后） | 新增 `practice_office` 子地点，走进去再升级 | 中，要接地图/步行/测试 | 需要办公室场景时再做 |

先做 A：它已经满足“进入练习室以后有个办公室”的操作感，又不会为了一个面板改地图。等办公室要放剧情/对话时，再升级成 B。

**数据模型（草案）**：

```ts
type FacilityLevel = {
  level: number;
  cost: number;
  requires?: Condition[];
  description: string;
};

type FacilityDef = {
  id: 'vocal' | 'dance' | 'expression';
  name: string;        // 声乐室
  locationId: 'practice_room';
  activityId: string;  // vocal / dance / expression
  varKey: string;      // facility.vocal
  levels: FacilityLevel[];
};
```

- `FacilityDef` 是结构内容，放 TS，不走审查台；
- 等级存 `vars`，不加存档字段；
- `ActivityDef.levels` 用 `requires: [{ varAtLeast: 'facility.vocal', value: 1 }]` 读同一个 `varKey`；`FacilityDef` 只负责面板、费用和文案；
- 升级命令 `upgradeFacility(state, facilityId)`：检查地点/阶段/等级/金钱 → 扣钱 → 写 `vars` → 日志；
- `resolveActivity` 根据 `vars` 选当前等级，不需要知道设施的存在。

### 3.1 目标

```text
声乐课（初级）  60 分钟 · ¥150 · 体力 15 · EXP +2
中级声乐课      50 分钟 · ¥150 · 体力 15 · EXP +3
高级声乐课      40 分钟 · ¥150 · 体力 15 · EXP +4
顶级声乐课      30 分钟 · ¥150 · 体力 15 · EXP +5
```

三个房间同表，只是属性不同。升级后**旧选项消失**，界面只显示当前等级；不是叠加四个按钮。

### 3.2 关键约束：不能换 action id

实测正式包里锚定在三个训练行动上的事件：

```text
vocal       27 条
dance       29 条
expression  26 条
合计        82 条
```

如果中级训练改用新 id（如 `vocal_2`），这 82 条 `after.ids: ['vocal']` 全部失效，而且新增角色时还会继续踩。**结论：必须保留基础 action id，用“等级解析”换数值和文案。**

### 3.3 数据模型

```ts
type ActivityLevel = {
  /** 1 起；0 是基础行动本身。 */
  level: number;
  requires?: Condition[];
  name?: string;
  description?: string;
  durationMinutes?: number;
  cost?: Cost;
  effects?: Effect[];
  resultTexts?: string[];
};

type ActivityDef = {
  // ...现有字段
  levels?: ActivityLevel[];
};
```

新增纯函数：

```ts
resolveActivity(state, activity): ActivityDef
```

- 没有 `levels` 时原样返回；
- 否则从高到低找第一个 `requires` 全部满足的等级，把覆盖字段合到基础行动上；
- 返回的 `id` 仍是基础 id。
- **覆盖是整字段替换，不是增量**：`effects` 一旦写了，就要把属性 EXP、压力等写全；否则会丢效果。

接入点（缺一不可）：

- `activityCost` / `activityDuration` / `activityStaminaCost`；
- `applyActivity` / `applyActivityDef` 的结算与结果文案；
- `scene.ts` 的按钮名称、描述、消耗预告，以及行动结果页 `buildActivityResult`；
- `canStartActivity` 的禁用原因；
- 事件上下文 `lastActivityId` 仍写基础 id。

### 3.4 等级数值（四档，三个房间同表）

用户已定：四档 **初级 / 中级 / 高级 / 顶级**；每升一级 **时间 −10 分钟、EXP +1、金钱不变**；每次 **体力 15**。

| 等级 | 时间 | 体力 | 金钱 | EXP | EXP/体力 |
|---|---:|---:|---:|---:|---:|
| 初级 | 60 | 15 | ¥150 | 2 | 0.133 |
| 中级 | 50 | 15 | ¥150 | 3 | 0.200 |
| 高级 | 40 | 15 | ¥150 | 4 | 0.267 |
| 顶级 | 30 | 15 | ¥150 | 5 | 0.333 |

- **三个房间（声乐/舞蹈/表现）同表**，只是属性不同；不再保留旧的“舞蹈更耗体力、表现更便宜”的差异。
- **金钱不变**是刻意的：升级不会让日常训练变便宜，钱坑不会被升级削掉。
- 时间 60→30 分钟、EXP 2→5，EXP/小时从 2 提到 10；升级收益是“更快、更多”，不是“更省”。
- **旧 125% 上限不再适用**：顶级是初级的 2.5 倍 EXP，硬套 125% 会卡死设计。旧锚点（1 体力 = 0.25 EXP）只适用于旧的 30 分钟课程；设施是新曲线。
- 体力统一 15：F 级体力上限 100，刚好 **6 次/轮**；休息 +30 约换 2 次。F→E 的 10 次课需要中途休息。
- 压力暂不变；时间缩短后单位时间压力更高，休息仍是约束。

### 3.5 升级费用

| 升级 | 费用 |
|---|---:|
| 初级 → 中级 | ¥5,000 |
| 中级 → 高级 | ¥10,000 |
| 高级 → 顶级 | ¥15,000 |

- 每间房满级共 **¥30,000**，三间共 **¥90,000**。
- 升级是设施面板里的命令，不消耗时间；费用写进 `FacilityDef.levels`，逻辑不变。
- 门槛：当前**不设属性/天数门槛**，钱就是门槛。
- 升级后旧训练选项消失，新选项按等级解析出现。

> **早期经济评估（已按 ¥150 / 15 体力重算）**：F→E 需要 20 EXP；初级 2 EXP/次 = **10 次 × 60 分钟 = 10 小时，¥1,500**，占开局 ¥3,000 的 **50%**。
> 体力 100 只够 6 次，需要休息两轮；第一天基本排满。
> 结束 F→E 后剩 ¥1,500，容错明显好转；即使不接工作也能继续练 10 次。早期不再有“刚好归零”的问题。

### 3.6 可行性与可玩性

**可行性：中高。** 等级存 `vars`，不需要新存档字段；但需要新增 `FacilityDef` / 设施面板 / 升级命令，并改 `types` / `scene` / `sim` / UI。约 3–5 天系统 + 1–2 天内容与平衡。

**可玩性：高。** “旧选项被替换”比“多一个按钮”更有升级感；三个房间让玩家自己决定先练哪条线，钱有明确用途。

**五个风险**：

1. **早期预算偏紧但可控**。F→E 要 10 次初级课 = ¥1,500 / 10 小时，占开局 ¥3,000 的 50%；结束剩 ¥1,500，可以继续练或留作缓冲。体力仍需两轮休息，第一天时间会很满。
2. **升级不降日常支出**。金钱固定 ¥150 是好事（钱坑不被升级削掉），但日常训练仍比旧课程 ¥120 略贵；一天 6–8 次就是 ¥900–1,200。
3. **三个房间被体力统一抹平**。体力统一 15 后，声乐/舞蹈/表现只在“练哪个属性”上不同，不再有“舞蹈更贵、表现更省”的差异；早期 EXP/体力只有 0.133，比旧课程低。
4. **事件锚点**。只要保留基础 id 就安全；已用 82 条事件做回归，`activityLevels.test` 断言每级 id 仍是基础 id。
5. **三个房间的面板会膨胀**。一行一个房间、只显示“当前 → 下一级”，不要把每一级的完整数值都铺开；详情留给展开行。

### 3.7 不推荐的替代方案

- **新 id + 改 82 个锚点**：脆弱，新增角色必踩，且 `after` 选择器会越来越长。
- **只改 `activityCost` 动态读 `vars`**：按钮名称和 EXP 仍是旧的，无法表达“中级/高级”，也改不了结果文案。

## 4. 经济影响与验收

### 4.1 预算

| 项 | 量级 |
|---|---:|
| 设施总出口 | **¥90,000**（三间房各 ¥30,000） |
| 现有礼物总出口 | ¥4,400（改冷却后变为持续小额） |
| 日均训练支出 | 约 ¥900–1,200（6–8 次 × ¥150） |
| 日均净剩 | 约 ¥1,650–1,950（按工作收入 ¥2,850 上限估算） |
| 设施回本 | 约 46–55 天；长线，但已可接受 |

> ¥150 让日常训练不再压死现金流，主要的一次性出口仍是 ¥90,000 的设施升级。

### 4.2 必须补的测试

- `shop cooldown`：买 → 冷却中拒绝 → 推进时间 → 可买；读档后冷却保留。
- 永久限购：`maxPurchases: 1` 买完后永久售罄，不显示倒计时。
- 存档迁移：v18 旧档补 `shopCooldowns`。
- `resolveActivity`：四档（初级/中级/高级/顶级）的名称、时间、金钱、EXP；`requires` 不满足时回退。
- **UI 与结算同源**：按钮预告的时间/金钱/EXP 必须与实际 `applyActivity` 扣的一致（升级后最容易分叉的地方）。
- 事件锚点：升级后 `after: { ids: ['vocal'] }` 仍触发（至少每条训练 1 条 E2E 或单测）。
- 数值：四档固定为 60/50/40/30 分钟、2/3/4/5 EXP、¥150、体力 15；升级费用 5k/10k/15k。
- 早期经济：跑一次“新游戏 → 只训练声乐”的模拟，确认 F→E 花掉约 ¥1,500 后仍剩 ¥1,500，且不会出现负现金。
- UI：升级后旧按钮消失，新按钮显示新名称/新消耗。
- 设施面板：三个房间独立升，升一个不影响另外两个；钱不够/等级不够时按钮禁用并给原因。
- 设施数据一致性：每个 `FacilityDef.levels` 都要有对应的 `ActivityLevel.requires`，升级后真的能切到新训练。

### 4.3 机器门

- `content:audit` 增加：`cooldownMinutes` / `maxPurchases` 必须是正数；`levels` 的 `requires` 引用合法；`FacilityDef.activityId` / `varKey` 引用合法。
- `npm run build` 仍要过类型检查与内容体检。
- 若要更稳，加一个 `content:economy` 脚本，跑 30 天简单策略，输出金钱曲线与训练支出。
