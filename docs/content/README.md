# 内容生产

> 这里放**生产规范、流程、块清单与进度**。  
> 批量生产一个角色时先看 [playbook.md](playbook.md)——交付协议、覆盖矩阵、写作配方都在那儿。
> 数值档位在 [`docs/current/content-standards.md`](../current/content-standards.md)。
> 审查系统在 [`docs/systems/content-review.md`](../systems/content-review.md)。
> 角色语气以 **官方剧情中译语料库** 为准，见各角色卡第 12 节。

## 1. 目录

```text
docs/content/
  README.md              本文件：规范 + 流程 + 块清单 + 进度
  mano/
    character.md         真乃的角色卡（写作时逐条对照）
```

一个角色一个目录。第二个偶像上线时新建 `docs/content/<idol>/`。

---

## 2. 两种内容，两条路径

动手前先判断你要写的是哪一种：

| | 结构 | 条目 |
|---|---|---|
| 举例 | 偶像、日程、地点、交通、地图、饰品、初始状态 | 行动、事件、工作、对话、剧情链、物品、商店 |
| 写在哪 | `src/core/content/*.ts` | **审查台草稿** → `content-review/approved/` |
| 谁审 | 代码评审 | 人（审查台） |
| 为什么 | 它们是"骨架"，改一条会影响全局引用 | 它们是"文本 + 数值"，一条条可批注 |

**判断标准**：这条东西能不能被单独打回重写？能 → 条目；会连累别的引用 → 结构。

---

## 3. 生产单位：一个块

**一个块 = 一个归属 × 一个挂载点 × 一种内容单元。**

例：「真乃 · 训练后 · 事件」是一个块。「真乃 · 偶像页 · 行动」是另一个块。两者不重叠，各自验收。

不用「日常 / 严肃 / 温馨」这种分法——不可验证，而且同一条内容能同时属于两类，最后会重复生产或漏掉。

| 轴 | 取值 |
|---|---|
| 归属 | 单个偶像 / 全员通用 / 制作人 / 地点 / 系统 |
| 挂载点 | 偶像页 / 地点页 / 行动后 / 到达 / 定时 / 延迟 / 剧情链步骤 / NPC 话题 |
| 单元 | 行动 / 事件 / 对话 / 剧情链 / 工作 / 物品·商店 / 话题 |

---

## 4. 流程

```text
1. 定坐标      写进本文件的块表（归属 / 挂载点 / 单元）
2. 查角色卡    语气、称呼、阶段态度、OOC 对照
3. 查数值档位  时长 / 体力 / 钱 / EXP / 粉丝 / 冷却
4. 写草稿      npm run review → 新建（id 带块号）
5. 过审查台    预览 → 批注 → 打回 → 改 → 通过
6. 进游戏玩    npm run build → 真的触发一次
7. 记状态      块表标记完成，写一句"学到了什么"
```

第 6 步不能省。只在审查台看预览，看不出时序、抢占、排版。

### 通过之后发生什么

```text
content-review/approved/*.json
      │  npm run content:sync（审批时自动、构建门也自动）
      ▼
src/core/content/approved.generated.ts   ← 生成物，不要手改
      ▼
PRODUCTION_PACK = BASE_PACK + approved    ← 游戏加载的就是它
```

所以你**不需要**手动改 TS，也不要两边都留一份。

## 5. 硬规则

写内容时踩过、以后不能再踩的：

1. **kind 只有一份清单**：`REVIEW_KINDS`。类型、校验、插件、读取脚本都从它派生。加一种内容类型只改这一处。
2. **加字段就要想存档**：给会被存档的结构加成员（属性、状态位），必须同时写迁移并升 `SAVE_VERSION`，否则老档白屏。
3. **不要在运行时用 `import.meta.glob`**：构建产物里它不存在，任何判空都会让整批内容静默变空。
4. **内容走审查台，结构留 TS**。不要为了省事把一条文本硬编码进 `src/core/content`。
5. **高报酬的工作必须有检定**：没有检定的高报酬等于签到。
6. **工作要给粉丝和属性**：只给钱的工作永远打不过 30 分钟零工。
7. **一份工作同时只能派一个人**，完成后进入 `cooldownDays` 冷却。
8. **剧情解锁用 flag**：剧情步骤写 `{ kind: 'flag', key, value: true }`，工作写 `requires: [{ kind: 'flag', key }]`。这类解锁再加 `hiddenUntilUnlocked: true`，解锁前整条从面板消失（属性/粉丝门槛照常显示，给玩家方向）。
9. **事件没有文本变体**（对话节点才有）。高频锚点写多条 `once`，不要写一条循环。
10. **`after` / `afterIdol` 只对偶像页行动生效**；地点页行动没有偶像上下文，用 `castPresent` 代替。
11. **密度先低后高**：一个块 3–8 条。先让整条链路跑通，再回头加量。

## 6. 解锁一份工作

三种门槛，写法都是 `JobDef.requires`：

| 类型 | 条件 | 界面表现 | 用在哪 |
|---|---|---|---|
| 属性 | `{ kind: 'attributeAtLeast', ref, rank }` | 列表显示「未解锁」 | 引导玩家练某个属性 |
| 粉丝 | `{ kind: 'fansAtLeast', value }` | 列表显示「未解锁」 | 里程碑式的大活 |
| 剧情 | `{ kind: 'flag', key }` + `hiddenUntilUnlocked: true` | **整条消失** | 剧情推进的奖励，不剧透 |

剧情解锁的完整写法：

```jsonc
// 剧情链的一步（或对话节点 / 选项）完成时
{ "effects": [{ "kind": "flag", "key": "unlocked.magazine_cover", "value": true }] }

// 工作
{
  "requires": [{ "kind": "flag", "key": "unlocked.magazine_cover" }],
  "hiddenUntilUnlocked": true
}
```

`content:audit` 会检查：**工作引用了某个 flag，但整包没有任何效果会设置它** → 警告 `job-unlock-flag`。
写错 key、改名忘改、剧情还没写就把工作挂上去，都会在这里被拦下。

## 8. 完成后自检（DoD）

一个块算完成，要同时满足：

- [ ] 条数在 3–8 之间
- [ ] 每条都过了 `npm run content:validate`（`content:audit` 0 错误）
- [ ] 每条都对照过角色卡的 10 条自查
- [ ] 至少一条选项「有代价」
- [ ] 在游戏里真的触发过一次（不是审查台预览）
- [ ] 没有新增未使用的 flag / var
- [ ] 工作类内容：有检定、有 `failureEffects`、有结果页文案、有冷却
- [ ] 带解锁的工作：`content:audit` 没有 `job-unlock-flag` 警告（剧情那条已经写好了）
- [ ] 块表标记完成

## 9. 命名

草稿 id 带块号，审查台队列本身就是进度表：

```text
draft.event.mano.b1.vocal
draft.activity.mano.b3.extra_practice
draft.dialogue.mano.b2.step3
```

内容 id 用领域前缀，不用块号（块号是生产期的，不该泄漏到内容里）：

```text
evt.mano.after_vocal      ✅
evt.mano.b1_after_vocal   ❌
```

## 11. 块记录
