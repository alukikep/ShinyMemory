# 内容生产手册

> 这份文档的目标：**让别人（或未来的我）不需要逐条讨论，就能按同样的标准批量生产一个角色的全部内容。**
>
> 规范细节在 [README.md](README.md)，数值在 [content-standards.md](../current/content-standards.md)，
> 系统在 [systems/](../systems/)。本文件只回答三件事：**怎么交给审查台、覆盖到什么程度、每类内容怎么写。**

---

## 0. 一句话流程

```text
角色卡 → 结构（TS）→ 草稿批次（审查台）→ 批量通过 → 构建 → 验收 → 记一笔
```

内容是**按块交付**的，不是按条讨论的。一个块的产出物是一个"批次包"，人只需要**通过 / 打回**。

---

## 1. 交付协议

### 1.1 我（生产者）每次交付什么

一个批次 = 一个块（3–8 条），交付时给这五项，**不多说**：

| # | 内容 | 例子 |
|---|---|---|
| 1 | 块编号与坐标 | `B3 · 真乃 · 偶像页 · 行动` |
| 2 | 草稿 id 列表 | `draft.activity.mano.extra_practice` … |
| 3 | 预检输出 | `npx tsx tools/content:validate` 与 `content:audit` 的结果 |
| 4 | 一句为什么 | 「专属行动不给粉丝，是为了不抢工作的生态位」 |
| 5 | 最多一个开放问题 | 「三个选项都同价，还是要一好一坏？」 |

### 1.2 人（审查者）只需要做什么

```text
通过 / 打回（打回时写一句原因）
```

打回不需要解释背景——一句「语气太活泼」就够，我按这句话重写，不辩解、不追问。

### 1.3 什么情况必须问，什么情况自己定

| 必须问 | 自己定 |
|---|---|
| 新增机制（新的条件/效果/系统） | 文案、选项措辞、结果文本 |
| 改已通过内容的语义 | 同一档位内的数值微调（±20% 以内） |
| 删除任何已通过内容 | 块内条数、排序、命名 |
| 数值档位本身的调整 | 解锁条件用哪个 flag |
| 跨角色的结构（日程、地点） | 冷却天数在档位内的取值 |

**没人可问时的默认动作**：选更保守的那个（数值更小、暴露更少、更容易改回来），并在交付说明里标一句「这里是按 X 定的」。

## 2. 新角色接入：一份清单

按顺序做，每一步完成再进下一步。以「真乃」为样板。

| # | 步骤 | 产出 | 在哪 |
|---|---|---|---|
| 1 | 角色卡 | 语气、称呼、阶段态度、OOC 对照、语料用法 | `docs/content/<id>/character.md` |
| 2 | 偶像定义 | id、名字、组合、颜色、头像、成长曲线 | `src/core/content/idols/<id>.ts` |
| 3 | 角色日程 | 一周作息（她在哪、什么时候、能不能被工作顶掉） | `src/core/content/actors/<id>.ts` |
| 4 | 招募链 | 2–3 步剧情链 + 对话，从「认识」到「招募」 | `storyChains.ts` + `dialogues/<id>.ts` |
| 5 | 训练与自由时间 | 至少 4 条偶像页行动 | 审查台批次 |
| 6 | 专属行动 | 1–3 条，挂在她作息的空档 | 审查台批次 |
| 7 | 日常话题 | 6–8 条闲聊，24 小时冷却 | 审查台批次 |
| 8 | 训练后事件 | 每个训练行动 1 条 | 审查台批次 |
| 9 | 工作线 | 她的属性对应的 2–3 份工作 | 审查台批次 |
| 10 | 长线剧情 | 3 步 + 分支，带一次解锁 | 审查台批次 + 结构 |
| 11 | 验收 | 游戏里真的走一遍 | `npm run acceptance` |
| 12 | 记录 | 块表 + 一条经验 | `docs/content/README.md` |

第 2–4 步是结构（直接写 TS，不需要审查）；第 5–10 步全部走审查台。

## 3. 覆盖矩阵：做到什么程度算"全覆盖"

一个角色成熟时应该有这么多内容。**不是每个角色都必须满编**，但缺哪块要说得出来。

| 单元 | 建议条数 | 挂载点 | 必须性 |
|---|---:|---|---|
| 训练行动 | 3 | 偶像页 · 常驻 | ✅ 必须 |
| 自由时间 | 1 | 偶像页 · 常驻 | ✅ 必须 |
| 专属行动 | 1–3 | 偶像页 · 作息空档 | ✅ 至少 1 |
| 日常话题 | 6–8 | 偶像页 · 每天 3 次 | ✅ 至少 6 |
| 训练后事件 | 3–5 | 行动后 · `after` | ✅ 必须 |
| 地点事件 | 2–4 | 地点页 · `castPresent` | 🟡 建议 |
| 到达事件 | 0–2 | `entry.kind = arrival` | 🟡 可选 |
| 定时事件 | 0–2 | `trigger` | 🟡 可选 |
| 工作 | 2–3 | 事务所 · 有冷却 | ✅ 至少 2 |
| 剧情链 | 2 条（招募 + 长线） | 地点页 · 步骤 | ✅ 必须 |
| 对话 | 跟随剧情 / 事件 | — | ✅ 必须 |
| 物品 / 商店 | 跟随地点经济 | 店铺 | 🟡 按地点 |

**总时长目标**：一个角色从招募到"第一周有内容可做"，大约需要 **20–25 条**（不含对话节点）。

## 4. 写作配方

每类内容一份模板。所有数值都在 [content-standards.md](../current/content-standards.md) 里，这里只列**必填字段**和**最容易错的点**。

### 4.1 训练行动（偶像页）

```jsonc
{
  "id": "activity.<idol>.vocal",
  "name": "声乐课",
  "kind": "training",
  "target": "present-idol",
  "idolIds": ["<idol>"],          // 专属就写，全员通用可省
  "locations": ["practice_room"],
  "durationMinutes": 30,
  "timeWindows": [{ "fromMinute": 480, "toMinute": 1200 }],
  "cost": { "stamina": 12, "money": 120 },
  "effects": [
    { "kind": "attributeExp", "ref": "vocal", "tier": 3 },
    { "kind": "sharedStat", "stat": "stress", "delta": 5 }
  ],
  "resultTexts": ["…", "…"]        // 至少 2 条，别写一句循环用
}
```

- 档位：30 分钟 / 体力 10–15 / ¥120 / EXP +3 / 压力 +4–6
- ❌ 最常见错误：写 `fans`。训练不涨粉。

### 4.2 专属行动（偶像页 · 作息空档）

- 档位：30 分钟 / 体力 3–8 / **不花钱** / 信任 +5 / 属性 +1 / **不给粉丝**
- 她的作息里必须真的在那个地点那个时间，否则按钮永远不会出现
- 写法是「她在做自己的事」，制作人旁观或陪一段

### 4.3 日常话题（偶像页 · 闲聊池）

```jsonc
{
  "id": "<idol>.chat.<topic>",
  "actorId": "<idol>",
  "label": "今天怎么样",
  "text": "「……嗯。还行。」",
  "cooldownMinutes": 1440,
  "effects": [{ "kind": "attributeExp", "ref": "trust", "tier": 1 }]
}
```

- 每条 24 小时冷却、信任 +1
- 页面上只显示一个「聊两句」，**不要**给每条单独做按钮
- 一次 15 分钟、每天最多 3 次由系统管，内容侧不用重复限制

### 4.4 工作（事务所 · 面板）

```jsonc
{
  "id": "job.<name>",
  "name": "摄影棚拍摄",
  "locationId": "studio",
  "fromMinute": 600, "toMinute": 720,
  "pay": 1200,
  "check": { "ref": "expression", "difficulty": "E" },
  "failurePayRatio": 0.4,
  "cooldownDays": 2,
  "requires": [{ "kind": "fansAtLeast", "value": 500 }],   // 或 flag
  "hiddenUntilUnlocked": true,                              // 剧情解锁才用
  "effects": [
    { "kind": "fans", "value": 120 },
    { "kind": "attributeExp", "ref": "expression", "tier": 10 }
  ],
  "failureEffects": [{ "kind": "sharedStat", "stat": "stress", "delta": 12 }],
  "resultTexts": ["…"], "failureTexts": ["…"]
}
```

- **必须有检定**；没有检定的高报酬工作 = 签到
- **必须给粉丝和属性**；只给钱永远打不过 30 分钟零工
- 冷却 2 天（常规）/ 4 天（大活）
- 每个属性至少对应一份工作，否则那条属性没有出口

### 4.5 事件

```jsonc
{
  "id": "evt.<idol>.<anchor>",
  "title": "…",
  "after": { "ids": ["vocal"] },        // 偶像页行动用 after + afterIdol
  "afterIdol": { "ids": ["<idol>"] },   // 地点页行动改用 castPresent
  "chance": 0.4, "priority": 5, "once": true,
  "text": "…",
  "choices": [
    { "label": "…", "hint": "信任 +3", "effects": [...], "result": "…" }
  ]
}
```

- **事件没有文本变体**（对话才有）→ 高频锚点写多条 `once`，不要写一条循环
- 至少一个选项「有代价」
- 结果文本要回应选项，不是重复选项

### 4.6 对话与剧情链

- 对话节点可以有 `textVariants`（按条件换台词）
- 剧情链每一步：`locationId` + `timeWindow` + `dialogueId` + `actionLabel`
- 解锁用 `effects: [{ kind: 'flag', key: 'unlocked.xxx', value: true }]`
- 长线剧情要有分支，选项之间**代价不同**而不是都 +1

### 4.7 物品与商店

- 物品：价格 200–800、`maxPurchases` 控制稀有度
- 商店：`itemIds` 决定货架（物品不反向引用商店）

## 5. 数值联动：三类内容的时间预算

一天 08:00–22:00 = 14 小时 = 28 个 30 分钟格。内容设计要按这个算：

| 用途 | 单次 | 一天上限 | 备注 |
|---|---|---|---|
| 训练 | 30 分钟 | 被她所在的地点和体力限制 | ¥120/次，EXP +3 |
| 制作人零工 | 30 分钟 | 体力限制 | ¥0–280 + 制作人属性 +3 |
| 闲聊 | 15 分钟 | **3 次** | 信任 +1 |
| 工作 | 替换她整天 | 每天最多 1 份/人 | 粉丝主要来源 |
| 专属行动 | 30 分钟 | 受作息窗口限制 | 信任 +5 |

**粉丝曲线**（验收基准）：第 7 天 800–1,200。达不到就说明工作数量不够或冷却太长。

## 6. 质量门

### 6.1 自动（每次交付前跑）

```bash
npx tsc --noEmit                 # 类型
npm test                         # 单元（跑夹具包）
npx tsx tools/contentAudit.ts    # 内容体检
npm run acceptance               # 引擎 + 内容 E2E
npm run acceptance:prologue      # 正式包 E2E
```

体检必须 **0 错误**；警告要么修，要么在交付说明里解释为什么留着。

### 6.2 人工（每条内容对照角色卡）

- [ ] 语气符合角色卡第 2、3 节
- [ ] 没有 OOC 对照表里的词
- [ ] 称呼正确（她怎么叫制作人）
- [ ] 阶段态度正确（招募前 / 后不同）
- [ ] 结果文本回应了选项，不是复述
- [ ] 至少一条选项有代价
- [ ] 没有出现「她很开心」这种直接说情绪，改成动作

### 6.3 数据（每批结束后）

```text
粉丝第 7 天是否落在 800–1,200
钱是否在第 4 天前见底（是 → 报酬太高或工作太少）
训练是否还有人做（没人做 → 工作的属性回报太高）
```

## 7. 常见坑（全部是真实事故）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 同一份逻辑写两遍 | 通过的内容进不了游戏 | 抽成一个函数 + 一条两边一致的测试 |
| 运行时用 `import.meta.glob` | 构建后内容静默变空 | 生成文件（`content:sync`） |
| 给存档结构加字段没写迁移 | 老档白屏 | 升 `SAVE_VERSION` + 写迁移 + 一条迁移测试 |
| 用展示文案做判定 | flag 未满足被当成已满足 | 判定走 `checkCondition`，文案只用于显示 |
| 命令没生效却不提示 | 按钮像坏了 | 状态没变时写一条日志 |
| 事件被当成其他类型解析 | 体检报 `choices is not iterable` | 类型清单只有一份（`REVIEW_KINDS`） |
| 地点页按钮一多就挤 | 体验崩塌 | 一个入口 + 两级面板 |
| 专属行动比训练强 | 训练失去意义 | 专属行动给信任，训练给属性 |

## 8. 命名与编号

```text
草稿 id： draft.<kind>.<idol>.<block>.<slug>      draft.event.mano.b1.vocal
内容 id： <领域>.<idol>.<slug>                     evt.mano.after_vocal
块号：   B1 B2 B3 …（只在草稿和文档里出现，不进内容 id）
flag：   unlocked.<工作id> / seen:<话题id>（系统生成的不用手写）
```

编号的意义：审查台队列本身就是进度表，看 id 就知道属于哪块。

## 9. 复制即用的骨架

```jsonc
// 草稿外层（审查台读的格式）
{
  "id": "draft.<kind>.<idol>.<block>.<slug>",
  "kind": "activity",           // activity|event|job|dialogue|story|item|shop|topic
  "title": "给审查台看的标题",
  "status": "review",
  "version": 1,
  "rootId": "draft.<kind>.<idol>.<block>.<slug>",
  "payload": { },               // 真正的定义
  "annotations": [],
  "createdAt": "…", "updatedAt": "…",
  "history": [{ "status": "review", "at": "…" }]
}
```

修订已通过的内容时：`version` +1、`supersedes` 填旧草稿 id、`rootId` 保持不变。通过后旧版自动转 `discarded`。

## 10. 一轮生产结束后记什么

在 `docs/content/README.md` 的块记录里追加三行：

```text
B3 2026-10-30  3 条 / 通过 3 / 打回 0
   学到：专属行动必须先定"和训练差在哪"，否则会写成一堆便宜的训练
```

经验积累到 3 条以上，回填进角色卡的 OOC 对照表或本文档的第 7 节。
